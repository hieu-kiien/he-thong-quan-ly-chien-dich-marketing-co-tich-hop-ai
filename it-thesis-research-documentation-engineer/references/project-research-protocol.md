# Project Research Protocol

## Goal

Understand what the project really is before documenting it.

## Phase 1 — Evidence inventory

1. Read the assignment/rubric and thesis template.
2. Inventory repository structure, languages, dependencies, schema, tests, configs, deployment, and generated report artifacts.
3. Mark source-of-truth files for each subsystem.
4. Identify missing/unavailable evidence.
5. Declare the starting point: pre-existing materials versus project contributions.

## Phase 2 — Problem decomposition

Write:
- stakeholders;
- jobs/tasks;
- current pain points;
- desired outcomes;
- constraints;
- risks;
- data involved;
- system boundaries;
- external dependencies.

Do not begin with technologies. Begin with the problem and stakeholder needs.

## Phase 3 — Capability decomposition

Break the system into capabilities. Research comparable systems by capability, not title. For each capability identify:
- common architecture patterns;
- typical data model;
- quality concerns;
- security/privacy concerns;
- failure modes;
- measurable success criteria.

## Phase 4 — Research questions

Distinguish:
- descriptive: what exists / what is required?
- design: how should the artifact be designed under constraints?
- evaluative: how well does it meet objectives?
- explanatory: why did a design/result behave as observed?

## Phase 5 — Source hierarchy

Prefer primary official/current sources, peer-reviewed research, recognized academic books, and authoritative engineering documentation. Use blogs/community sources only when they add practitioner experience and label them accordingly.

## Phase 6 — Synthesis

Do not create a literature dump. Convert research into:
- design drivers;
- candidate alternatives;
- risk controls;
- evaluation criteria;
- justified exclusions.

## Phase 7 — Evidence gap report

Before writing final claims, list:
- known facts;
- disputed/inconsistent evidence;
- unknowns;
- proposed actions to verify them.
