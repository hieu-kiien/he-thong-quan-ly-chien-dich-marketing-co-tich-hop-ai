# Standards and High-Quality Reference Sources

Research date baseline: September 2026. Re-check current versions when recency matters.

## Software engineering body of knowledge
- IEEE Computer Society, SWEBOK Guide V4.0 (2024). Use as a broad map of requirements, architecture, design, construction, testing, operations, maintenance, configuration management, management, process, quality, security, professional practice, economics, and foundations.
  https://www.computer.org/education/bodies-of-knowledge/software-engineering

## Requirements
- ISO/IEC/IEEE 29148:2018, Requirements engineering. Confirmed current by ISO in 2024; ISO notes a replacement draft is in progress. Use as a requirements-process/content benchmark, not as a claim of formal compliance unless the project actually demonstrates conformance.
  https://www.iso.org/standard/72089.html

## Architecture documentation
- ISO/IEC/IEEE 42010:2022, Architecture description. Current published edition at research time.
  https://www.iso.org/standard/74393.html
- CMU Software Engineering Institute, Views and Beyond. Use stakeholder/view-based documentation, view selection, rationale, interfaces, behavior, and beyond-view information.
  https://www.sei.cmu.edu/library/views-and-beyond-collection/

## Software quality
- ISO/IEC 25010:2023, Product quality model. Use to identify relevant quality characteristics and measurable design drivers.
  https://www.iso.org/standard/78176.html

## Design description
- IEEE 1016-2009 is inactive-reserved as of research time. It can be used as a historical/content-organization reference for software design descriptions, not represented as a current active standard.
  https://standards.ieee.org/ieee/1016/4502/

## Research / design science
- Peffers et al., Design Science Research Methodology: problem identification, objectives, design/development, demonstration, evaluation, communication.
  https://www.jmis-web.org/articles/765
- Roel Wieringa, Design Science Methodology for Information Systems and Software Engineering. Useful for design problems, knowledge questions, and validation.
  https://link.springer.com/book/10.1007/978-3-662-43839-8

## Verification and validation
- NASA Systems Engineering Handbook appendices: good-requirement guidance, requirements verification matrix, validation matrix, V&V planning. Adapt concepts to software project scale.
  https://www.nasa.gov/reference/system-engineering-handbook-appendix/

## Security
- NIST SP 800-218 SSDF 1.1 is final at research time. Version 1.2 exists as a public draft; do not describe draft content as final.
  https://csrc.nist.gov/pubs/sp/800/218/final
- OWASP Threat Modeling Cheat Sheet.
  https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html
- OWASP ASVS 5.0.0 is listed by OWASP as the latest stable version at research time.
  https://owasp.org/projects/asvs

## AI
- NIST AI RMF 1.0 and NIST AI 600-1 Generative AI Profile. Note that NIST states AI RMF 1.0 is under revision at research time.
  https://www.nist.gov/itl/ai-risk-management-framework
  https://www.nist.gov/publications/artificial-intelligence-risk-management-framework-generative-artificial-intelligence
- Google People + AI Guidebook for human-centered AI design patterns and explanation/feedback/product behavior.
  https://pair.withgoogle.com/guidebook-v2/

## Architecture quality question banks
- AWS Well-Architected: operational excellence, security, reliability, performance efficiency, cost optimization, sustainability.
  https://docs.aws.amazon.com/wellarchitected/latest/framework/
- Microsoft Azure Architecture Center / Well-Architected Framework: business-driven design, reliability, security, cost, operational excellence, performance.
  https://learn.microsoft.com/en-us/azure/architecture/
  https://learn.microsoft.com/en-us/azure/well-architected/

Use these as review frameworks. Do not claim a project is “Well-Architected” merely because questions were consulted.

## Operations
- Google SRE Workbook: SLOs, monitoring, alerting, toil reduction, simplicity and reliability practices.
  https://sre.google/workbook/part-I-foundations/

## University project/dissertation benchmarks
- Cambridge Computer Science Part II dissertation guidance: explicit starting point, requirements analysis/professional preparation, implementation, repository overview, evaluation, conclusions.
  https://www.cst.cam.ac.uk/teaching/part-ii/projects/dissertation
- Cambridge project guidance: plan and present evidence that the result behaves as intended and communicate scientifically.
  https://www.cst.cam.ac.uk/teaching/part-ii/projects
- CMU capstone final report guidance: goals, architecture, detailed design/implementation, comparisons, experiments/evaluation.
  https://www.cs.cmu.edu/~prs/cap/Final.html
- Harvard CS systems project guidance: design detailed enough for replication; distinguish design from implementation; describe experimental setup and evaluation.
  https://read.seas.harvard.edu/cs261/2021/project/
- Stanford CS thesis proposal guidance: problem significance, state of the art, preliminary work/results, remaining work.
  https://www.cs.stanford.edu/phd-program-requirements-thesis-proposal
